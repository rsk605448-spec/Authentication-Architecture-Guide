# Authentication Code Walkthrough

This guide explains the implementation in the repository, tracing each HTTP endpoint into the helper functions and storage layer. It describes the current code—not a hypothetical production system.

## 1. Component map

| Component | Code | Responsibility |
|---|---|---|
| API and request validation | `app/main.py` | Defines FastAPI routes, validates credentials, maps failures to HTTP status codes, and protects the profile route. |
| Password and token helpers | `app/security.py` | Uses bcrypt for password hashing and PyJWT for signed access tokens. |
| User store | `app/store.py` | Stores normalized email addresses and password hashes in a process-local dictionary. |
| Configuration | `.env.example`, `.gitignore` | Shows the JWT secret setting and excludes the real local `.env` file from Git. |
| Tests | `tests/test_security.py` | Checks password hashing, token claims, and expiry rejection. |

## 2. Registration: password to stored hash

Endpoint: `POST /register` in `app/main.py`.

1. FastAPI parses the JSON body into the `Credentials` Pydantic model. Email length is limited to 3–254 characters; password length is limited to 8–128 characters.
2. `validate_email()` performs a basic email-shape check.
3. `get_user()` checks whether the normalized email already exists.
4. `hash_password()` in `app/security.py` calls `bcrypt.hashpw()` with `bcrypt.gensalt()`. The salt is generated by bcrypt.
5. `create_user()` in `app/store.py` stores the lowercase email and hash—not the submitted password.
6. The endpoint returns `201 Created` with a message and email only.

A duplicate account returns `409 Conflict`; invalid request fields or email shape return `422`.

## 3. Login: verify password and issue JWT

Endpoint: `POST /login` in `app/main.py`.

1. The API looks up the normalized email with `get_user()`.
2. `verify_password()` calls `bcrypt.checkpw()` to compare the submitted password with the stored hash. It does not decrypt the hash.
3. If the account is missing or the password is wrong, the route returns the same generic `401 Unauthorized` response.
4. If verification succeeds, `create_access_token()` builds a JWT with `sub`, `iat`, and `exp` claims.
5. PyJWT signs the token using HS256 and the configured `JWT_SECRET`.
6. The API returns `access_token` and `token_type: bearer`.

The access-token lifetime is 15 minutes, configured by `ACCESS_TOKEN_MINUTES` in `app/security.py`.

## 4. Protected request: bearer token to profile

Endpoint: `GET /me` in `app/main.py`.

1. The client sends `Authorization: Bearer <token>`.
2. FastAPI's `HTTPBearer` dependency extracts the bearer credentials.
3. `current_user()` calls `decode_access_token()`.
4. PyJWT verifies the signature and expiry using HS256 and the same configured secret.
5. The API reads the `sub` claim and looks up that user in the store.
6. A valid token and existing user produce the profile response. Missing, malformed, invalid, or expired credentials return `401 Unauthorized`.

The token is not a database session: each protected request verifies the signed token again.

## 5. Credentials and token safety

### Passwords

- Passwords are accepted only at registration and login.
- bcrypt creates a salted one-way password hash; the original password is not stored.
- The API does not return the password or hash.
- Passwords must not be logged or committed to source control.

### JWTs

| Claim / setting | Purpose |
|---|---|
| `sub` | Subject/user identity; this demo uses the email address. |
| `iat` | Issued-at timestamp. |
| `exp` | Expiry timestamp, 15 minutes after issuance. |
| `HS256` | HMAC-SHA256 signing algorithm. |
| `JWT_SECRET` | Shared secret used to sign and verify tokens. |

A JWT signature provides integrity and authenticity checks; it does not encrypt the payload. A bearer token is a credential: anyone who obtains a valid token can use it until it expires or the server otherwise rejects it. Keep claims minimal and never put passwords, API keys, or confidential information in them.

### Secret configuration

- Copy `.env.example` to `.env` and set a long, random `JWT_SECRET`.
- `.gitignore` excludes `.env`; never commit a real secret.
- `app/security.py` contains a development-only fallback secret to make the sample easier to run. It must be replaced through the environment for any deployment.
- Production systems should use a managed secret store and a deliberate key-rotation plan.

## 6. What this project does not implement

This is an educational example, not a production identity service. In particular:

- Users are held in an in-memory Python dictionary; data disappears on restart and is not shared safely across multiple workers.
- There is no refresh-token flow, logout endpoint, token revocation list, MFA, password reset, email verification, or role/permission authorization.
- The example's `/me` route authenticates the user but does not demonstrate fine-grained authorization.
- The demo has no rate limiting, persistent database constraints, audit logging, or production abuse controls.

Before production use, add persistent storage, HTTPS, strong secret management, rate limiting, monitoring, audit trails, revocation/rotation strategy, and security-focused integration tests.

## 7. Run and verify

Install dependencies, configure `JWT_SECRET`, then run:

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
pytest -q
```

Interactive API docs are available at `http://127.0.0.1:8000/docs` while the local server is running.
